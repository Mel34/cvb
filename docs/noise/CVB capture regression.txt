CVB capture regression — A/B/A test findings
- With Bash bracketed paste disabled, pasting two consecutive CVB path-capture commands followed by a normal printf command worked correctly; the clipboard contained the printf output.
- With bracketed paste enabled, the same sequence failed; the clipboard retained the contents of the second file instead of the printf output.
- Diagnostic logs showed suppression depth increasing from 0 to 4 as TargetRequest events and START markers interleaved, then remaining stuck at 3. Normal clipboard capture was consequently suppressed.
Question: Based strictly on these findings, what would you recommend as the smallest, most robust fix?




















Answer:
Recommendation: replace the CaptureSuppression depth counter with a boolean, and make it self-clearing. The counter assumes one START and one END per request, and bracketed paste breaks that assumption.
Why your findings point here
- With bracketed paste off, each pasted line gets its own prompt cycle, so START, request and END stay paired.
- With bracketed paste on, Bash gets the whole block in one readline return. Each command still fires PS0 (a START), but only one prompt (one END) follows.
- Your log shows depth going 0→4 and settling at 3. The current code increments on START-while-active and on every TargetRequest, but decrements only on END. A balanced counter can't work when the START/END ratio isn't 1:1.
The fix (all in pty.rs, about 15 lines)
Use a suppressed: bool that means "the command currently running was a path capture":
Event	New behavior
TargetRequest	suppressed = true; capture.end() (discard anything buffered)
Start	suppressed = false; capture.start(). A new command begins, so any earlier path-capture suppression is over.
End	If suppressed, set suppressed = false, call capture.end() and skip dispatch. Otherwise dispatch as today.


The key change is that START clears suppression instead of incrementing it. There is no depth to leak, and END always resets the flag, so a stuck state can't survive a prompt.
What it does for your pasted block
cvb a, cvb b, printf hi in one paste now gives:
1. START, request: suppressed.
2. START: suppression cleared and capture begins. Request: suppressed again, capture discarded.
3. START: cleared, capture begins. The printf output is buffered.
4. END: dispatches hi.
That matches the bracketed-paste-off result. If the block ends on a cvb <path>, END is discarded and the clipboard keeps the file contents, which is also correct.
Caveats
- Block with several commands: if the block mixes ordinary commands and a path capture, only the last command's output is dispatched. That is inherent, because there is one END per block.
- Ordering race: I'd keep the earlier note in mind. If more than 8 KiB of output is queued, the request could be handled before the START of the same cvb command. That START would then clear the suppression, and the bridge message could be captured. It's rare, and it can't wedge the session because the next END resets the flag.
- What I haven't seen: I don't have control.rs or bridge_paths, so I'm assuming the request is sent only once per cvb <path> invocation and the response is awaited synchronously.
Verification
1. Rewrite the three capture_suppression_tests for the boolean semantics, and add one test that replays the sequence above: START, request, START, request, START, data, END. Assert that exactly one dispatch happens, with the printf bytes.
2. Rerun your A/B/A test with bracketed paste on. The clipboard should now hold the printf output.
3. Keep the CVB_DEBUG_LOG depth field as a suppressed= field for one more session, to confirm it never stays true across a prompt.
I can write the patch and the tests when you're ready.

I traced this against the supplied pty.rs. The Boolean fixes the failure you reproduced but is not safe against the ordering race, and ordering alone can't make it safe. I haven't seen control.rs or the cvb client, so what the client prints and whether it waits for the response are unverified.
What the loop guarantees
- Handler order: Within one poll iteration, the master is read once (at most 8192 bytes) and its events are processed. Control messages are handled afterwards, in the same iteration.
- Causal order: Bash writes START to the PTY before command cvb runs, and the request is sent after that. Causally, START always comes first.
- Reader order: The proxy doesn't observe that order. handle_control_message can run before the START has been read from the master. Which inversions can happen:
  1. Backlog: More than 8 KiB is queued ahead of START, so one read doesn't reach it. The control branch still runs in the same iteration.
  2. Poll snapshot: master_events is taken at poll time. If the socket was readable but the master wasn't yet, the request is handled first. I believe PTY slave-to-master delivery goes through a kernel workqueue, so a small delay is plausible, but I'm not certain.
  3. Split marker: START straddles a read boundary, so the scanner emits it one read late. This is guaranteed by the code, since the scanner keeps a tail of up to 15 bytes (I said 13 earlier, which was wrong).
- END order: END is safe from this. The client can't exit until it receives the response, so END is emitted after the request was handled. This assumes the client blocks on the response, which I haven't seen.
Your log confirms the bug in normal order
Replaying the current code for cvb a, cvb b, printf in normal order:
Event	Depth
START1	0 (capture starts)
req1	1
START2	2
req2	3
START3	4
END	3


That is your 0→4 then 3 exactly, with no inversion needed. Bash fires PS0 once per parsed command but PROMPT_COMMAND once per prompt, so a block gives N STARTs and one END.
Sequences where the Boolean fails
1. Inverted request on the last command (wrong dispatch).
- Sequence: req, START, [client output], END.
- Result: req sets suppressed, START clears it and starts a capture, and END dispatches whatever the client printed. If it printed nothing, the clipboard becomes [NO_VISIBLE_OUTPUT], overwriting the file contents.
- It only matters for the last command before an END. For an earlier command in a block, a later START clears the flag harmlessly. Under the current counter, the same inversion leaks +1 permanently, so it may also be one of the real wedge triggers.
2. cvb a; printf hi on one line (wrong winner).
- There is one START, then the request, then the output, then END.
- The request discards the capture and END is suppressed, so the clipboard keeps the file contents rather than hi.
- This is deterministic and consistent in both orders. It is arguably acceptable, but it's a behavior choice.
3. cvb a & (late request).
- The request can arrive after END, or in the middle of the next command.
- Mid-command, it discards that unrelated command's capture and suppresses its END. The damage is bounded to one command, because the next START clears the flag.
What I recommend
- Smallest fix for the proven bug: Ship the Boolean. It resolves the paste-block wedge and cannot wedge, because the next START or END always clears it. Its remaining weakness is failure 1.
- Cheap diagnostic: Log target_request and start_seen with sequence numbers. A request whose seq precedes its own START would show how often failure 1 happens in practice.
- Robust fix (a follow-up): Make suppression in-band. The cvb() function in cvb-control.bash would print a third marker (for example ESC ] 777;CVB;PATHOP BEL) to /dev/tty before command cvb. /dev/tty rather than stdout, so a redirect like cvb a > f can't swallow it.
  - START, PATHOP and END are then all in one byte stream from one process, so their order is guaranteed.
  - The control socket would stop driving suppression entirely.
  - This needs a third marker in MarkerScanner and a few more lines in the control script. That's more than the Boolean's 15 lines, but it removes the race rather than shrinking it.
- Mitigation I'd skip: Draining the master before handling control fixes cause (a) of the inversion but not (b) or (c), and needs a non-blocking master.
Your second original example (Python edit, then cargo test) contained no path capture. The A/B/A result doesn't explain it, so I'd still check whether that session had an earlier cvb <path> in it.

CaptureState::start() does not clear an active capture (the repeated_start_keeps_existing_capture test), so a pasted block of ordinary commands dispatches all their outputs together at the one END. What the experiment showed
(<S> START, <P> PATHOP written by the cvb function to /dev/tty, <E> END)
Scenario	Marker stream
3-line block, paste off	S P out E, S P out E, S out E (one END per line)
3-line block, paste on	S P, S P, S hi, then a single E
cvb a; cvb b; echo hi	one S, two P, one E
cvb a > o.txt	S P E; o.txt contains only the client output
>/dev/null 2>&1, | cat, $(…)	P always lands between its S and E
cvb a & with a client that sleeps 0.4 s	S [1] 310 E, then the next command's S next E, then P at an idle prompt


That gives four conclusions:
- Order is guaranteed in-band. One process chain writes S, then P, then the client output, then E, and the PTY preserves that order. The control-socket race can't happen on this stream.
- Redirects don't affect the marker. /dev/tty bypasses fd 1 and 2. A marker written to stdout or stderr would have corrupted o.txt and the | cat input.
- PATHOP must be idempotent. Two P per S is normal, so any counter design breaks. The old depth counter and my Boolean were both exposed to this.
- A backgrounded job's marker is not attributable. Here it arrived after the next command's END, which is harmless. If it had arrived mid-command it would have killed that command's capture, a bounded one-command loss.
What the current wrapper does
- cvb-control.bash: cvb with all arguments existing becomes CVB_INTERNAL_TARGET=1 command cvb "$@". Anything else is plain command cvb "$@", which goes through normal output capture. The path decision is made in the shell, at call time.
- control.rs:
  - The client side has a blocking receive_one(), so I infer the client waits for TargetResponse.
  - It doesn't check the response id.
  - The channel is fd 3 and is inherited by every child process.
- Redirects: with socket-driven suppression, redirecting fd 1 or 2 is harmless today. cvb a 3>/dev/null or 3>&- breaks the request, because the client reads EOF and errors. That is a visible error, not a silent stale clipboard.
- Background and pipelines: cvb a & is asynchronous in the current code too. END dispatches [1] 310 and the bridge write lands whenever the client gets to it, so the final clipboard depends on timing.
Where PATHOP can be emitted
Emission point	Verdict
PS0 or PROMPT_COMMAND	No. They fire per command or prompt and can't know the command is a path capture.
Proxy, on TargetRequest	This is the current design, and it's the race.
cvb() in cvb-control.bash, only in the CVB_INTERNAL_TARGET branch, printed to /dev/tty	Works, and I tested it. It's speculative: if the client then fails before sending, the capture is already ended and the clipboard goes stale.
Client binary, immediately before ControlChannel::send(TargetRequest), writing to /dev/tty	Best. The marker and request are paired in one process, and the marker is emitted only when a request is really sent.


If the client can't be changed, use the shell function. It's the same coverage, because only the function sets CVB_INTERNAL_TARGET. In both cases, open /dev/tty and ignore failure; a missing controlling terminal just means no marker.
Proposed pty.rs change
- Scanner: make the marker table a list. Add \x1b]777;CVB;PATHOP\x07 (17 bytes), which makes the holdback 16 bytes.
- State: MarkerEvent::PathOp => capture.end(). Delete CaptureSuppression and its three tests, and drop its parameter from handle_control_message.
- Why that is enough: after capture.end(), nothing restarts capture until the next START. The existing if !capture.capturing { continue; } at END therefore skips dispatch, with no flag and no counter.
- Control socket: it keeps its job of running bridge_paths and replying, but no longer drives suppression.
Behavior of the stream-ordered cases:
Case	Result
Block cvb a, cvb b, echo hi	hi dispatched
cvb a; echo hi on one line	clipboard keeps a; the hi is lost (all-or-nothing per command)
Block ending in cvb a	END skipped; clipboard keeps a
Pasted block with echo 1 before cvb a	the 1 is discarded; it was going to be overwritten anyway


Residual risks
- Late PATHOP (&, or any request not synchronous with its command): bounded to one command's capture.
- Bridge write vs. an earlier END dispatch. The proxy can handle a request before it has read an earlier END. That needs a backlog or a slow dispatch, and I think it's very unlikely in practice. If your log ever shows it, defer bridge_paths until the matching PATHOP is scanned. That makes ordering fully stream-based and cvb a & deterministic. The cost is a pending-request queue and a client flag for "no marker emitted".
- Spoofing: any program that prints the raw marker bytes can alter capture. A per-session nonce in the marker would close that. I'd skip it unless you care.
One unrelated bug I noticed
I read this but did not execute it. MarkerScanner::finish() returns the withheld tail (up to 15 bytes), and proxy() writes it to stdout at exit. The raw chunk was already written to stdout before scanning, so those bytes are probably printed twice. Check whether exit appears twice when a session ends. If it does, finish() should discard its result instead.
